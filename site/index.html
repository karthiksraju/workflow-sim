Test what your Python workflow wrote after a failure.

A payment handler saves a receipt, the response is lost, and it retries. Did the customer get one receipt or two? workflow-sim runs the handler's real code against a modeled receipt service, on a virtual clock, and checks the final state.

It runs asyncio and Celery code in a fresh process each time. You choose the failures and write the checks. It's for Python developers whose background jobs call payment, email, storage or AI services and retry when something goes wrong.

One lost response, two possible outcomes

This is the billing example that ships with workflow-sim. A payment webhook sends a receipt. The receipt service saves it, but the response never arrives, so the handler retries.

  1. 0 sPayment handler sends the receipt for invoice in-42. The receipt service saves it.
  2. 0 sThe response is lost. The handler gets a TimeoutError.
  3. 2 sPayment handler waits two virtual seconds and sends it again.

Expected one receipt, found two. Exit code 1.

One receipt. Every check matched. Exit code 0.

The check you write (from examples/billing.py)

ctx.expect(
    'one exact receipt',
    lambda: list(account.receipts.values()),
    [{'invoice': 'in-42',
      'customer': 'cus-7',
      'amount': 1200}],
)

What the broken run reports (excerpt of result.json)

"outcome": "ASSERTION_FAILED",
...
"name": "one exact receipt",
"expected": [{"amount": 1200, "customer": "cus-7",
              "invoice": "in-42"}],
"actual":   [{"amount": 1200, "customer": "cus-7",
              "invoice": "in-42"},
             {"amount": 1200, "customer": "cus-7",
              "invoice": "in-42"}]

The receipt service here is a model we wrote: it saves by idempotency key, atomically. Whether your real provider behaves that way needs its own integration test. In the shipped example, the two key lines are one line switched by {"broken": true}.

Six examples to start from

Each example starts from existing state, has a corrected and a deliberately broken version, and checks final content. The data is synthetic.

WorkflowFailureWhat the check looks at
PaymentsReceipt saved, response lost, webhook delivered twicePaid account, exactly one receipt, event marked processed
Order fulfillmentPayment declines after stock is reservedOnly this order's stock is released; the older reservation stays; nothing ships
Data importInterrupted between row writes and the checkpointEvery row after restart, with no duplicates or gaps
Documents and AIOne chunk retries, another finishes lateAll chunks, in order, before the document is published
MonitoringRecovery and a new outage during an alert delayOnly the current incident sends its alert
MeetingsA new recording finishes before a stale oneThe stale result can't overwrite the new content

How to try it

  1. Get repository access

    The repository is private during the alpha. Ask for access first; the install step below needs it.

  2. Create a trial project with uv

    uv init --bare --python '>=3.12,<3.13' workflow-sim-trial
cd workflow-sim-trial
uv add 'workflow-sim @ git+ssh://git@github.com/karthiksraju/workflow-sim.git@v0.1.0a4'

    uv fetches a compatible Python. The git+ssh URL only works once your GitHub account has access.

  3. Run the billing example both ways

    uv run workflow-sim workflow_sim.examples.billing:build \
  --duration 12 --output billing.json
printf '{"broken":true}\n' > broken.json
uv run workflow-sim workflow_sim.examples.billing:build \
  --duration 12 --inputs broken.json --output billing-broken.json

    The first returns PASS (exit 0). The second returns ASSERTION_FAILED (exit 1) with two receipts in actual.

  4. Point it at one of your workflows

    Write a small adapter that calls your real entrypoint, swaps the services it calls for models, schedules the failure and checks the final state. Then put the bug back and confirm the same check fails. A check that never fails hasn't shown you anything.

What PASS means

PASS means every check you registered held in this modeled run. You write the models and the checks; workflow-sim doesn't generate them or verify a fix for you.

Checked in this run

  • Your workflow's real retry and write logic
  • The failures and timing you scheduled
  • The final state you asserted, including duplicates

Not proven by PASS

  • Production safety
  • The live provider, broker or database
  • Every possible task or thread interleaving

Celery is the only queue backend today. Adapters are trusted code and the worker is not a security sandbox, so run them without production credentials.
